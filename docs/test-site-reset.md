当前实现源码在 `src/test-site-reset/plugin/`，安装目录必须为 `clonewp-test-reset`。这是专用的单站维护工具，绑定 home/siteurl 域名 `yaoxuxuan.com`，不授予其他网站重置权限。

## 本次用户商品安排

用户已明确商品自行处理。本次配置不得运行“初始化 6 个测试商品及基础配置”按钮，不创建或修改商品、商品分类及商品图片。基础设置通过后台单独完成。用户准备好希望长期保留的商品后，再保存初始基准；捕获前重新核对实际页面和设置。尚未建立及实测基准时，不宣称恢复已可交付。

## 专用 API 连接状态

用户已明确授权长期保存本测试站凭据。当前默认连接已在 config/project.json 指向 yaoxuxuan.com，使用 config/credentials.yaoxuxuan.local.json；该文件仅含 Windows DPAPI 密文并被 Git 忽略，现有加载器通过当前 Windows 账户解密。WordPress 与 WooCommerce 凭据均在密文中保存，本轮仅用 WordPress 应用认证验证接口。

已通过：正式配置加载、WordPress REST 身份认证、页面编辑与上传权限、Novamira 能力发现、只读 PHP 返回正确域名及单项 Container 控件读取。完整组件自检仍出现响应中断，延长诊断也出现 MCP 请求超时，因此完整组件检查尚未通过；不要用基础连接通过替代后续建站能力验收。未修改商品、页面内容或服务端插件，未捕获基准或执行恢复。

## 初始化及基准

安装并启用 WoodMart 8.5.5、配套 WoodMart Core、Elementor 3.35.4、Elementor Pro 3.35.1、WooCommerce 和 Novamira。用户已选择自己安装 WoodMart、Core 和 Pro；不要争用其后台标签。Novamira AI abilities 的启用需另有当前用户确认。

恢复插件在 工具 → 测试站恢复 提供初始化入口：创建带原生附件的六个 WooCommerce 简单商品，其中一个促销、一个缺货；创建 WooCommerce 基础页面；设置站点标题、Asia/Taipei 时区、文章名链接及 noindex。初始化使用固定 SKU 和 `_clonewp_test_seed=v1` 所有权，不覆盖其他商品。初始化失败后先核对实际记录再继续；不可把成功响应当成前台验收。

完成真实前台、编辑器和查询检查后，保存初始基准。已有基准时，界面同时提供“覆盖保存当前状态为初始基准”和“恢复初始状态”；覆盖必须明确勾选确认，并匹配当前基准及 epoch。新快照完整保存且验证成功后才原子替换基准指向，旧备份保留，失败不替换原基准。恢复始终使用最后一次成功保存的基准。升级后不能未经验证沿用旧基准。

## 恢复范围

- 数据库：当前 WordPress 表前缀下的全部基础表，涵盖文章、页面、附件记录、商品、分类、菜单、模板、WoodMart 设置、Elementor 设置及插件业务表。保留当前 `users` 和 `usermeta`，不回滚密码、应用密码或登录会话。
- 文件：`wp-content/uploads`、`themes`、`plugins`、`mu-plugins`。恢复插件自身和请求网关必须与基准相符，并持续保留，避免中途失败后失去恢复入口。
- 不恢复 WordPress 核心、wp-config、服务器配置、CDN 及外部存储。WordPress 版本/域名/表前缀变化会拒绝旧基准。当前不支持 multisite、链接目录、缓存/数据库 drop-in、数据库视图、触发器、外键或生成列。

默认 vault 位于 WordPress 安装目录的父目录 `.clonewp-yaoxuxuan-vault`，必须位于实际公开目录外；也可由服务器管理员用 `CLONEWP_RESET_VAULT` 指定。数据库以 sodium secretstream 加密，密钥从当前 WordPress salts 在内存派生。清单经 HMAC 认证；文件复制和恢复均实际读回 SHA-256。不要在记录、报告或日志中保存认证信息。

## 串行、失败及对账

MU 请求网关为每个 WordPress 请求持共享文件锁。恢复操作建立维护标记，等待旧请求退出后持独占锁，再建立恢复前备份、验证基准、准备暂存文件和表，最后用一条 RENAME TABLE 切换数据库。预期基准 ID 和 epoch 防止过期后台页面重复执行。

每次恢复保留恢复前快照及被替换的文件/表；不会永久删除备份。这个版本不提供自动备份轮换，长期运行需监控磁盘。低于 512 MiB 时拒绝开始；复制过程中失败会保留证据并停在维护状态。

未知或部分恢复保留签名 pending 记录。管理员可通过 工具 → 测试站恢复 的“恢复操作前备份”进行回退；恢复期间保留登录和精确恢复入口。再次恢复不自动重试原写入。若存储不可写、PHP 无法启动或 WordPress 核心损坏，则必须由服务器管理员处理，插件不能代替服务器备份。

每次成功恢复生成新的 epoch。旧远端页面/媒体和任务所有权不再存在；cloneWP 旧任务必须重新读取实际站点并接受既有所有权/CAS 检查，不能拿旧 ID 继续写入。当前尚未实现自动扫描并改写本地历史任务状态的联动，不应声称已实现。

## 验证与交付要求

`tests/test-site-reset.test.ts` 调用真实 PHP 对加密截断/篡改、备份边界、认证保留、过期状态、文件与数据库编排、部分失败回退作本地验证。SQL fixture 仅验证编排，不证明实际 MySQL 权限、原子切换或 WordPress 插件兼容。

远端必须另做：依赖和 PHP sodium/vault 权限检查 → 六个商品及附件读回 → 当前前台/编辑器检查 → 建立基准 → 创建具名可丢弃页面/媒体/菜单或配置变化 → 执行恢复 → 确认清除、商品保留、版本与配置保留、epoch 更新、登录及 Novamira 仍可用。失败时保留 pending 和恢复前备份，不标记完成。交付报告列出实际资源名称、ID、状态和后台链接，并明确未验证能力。
