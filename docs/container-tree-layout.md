# 容器树与内容对齐线

与 [通用三步复刻](three-step-replica.md) 共用制作依据。整体对齐是内部组之间的关系，不是所有图文强制等高；分别判断顶部、居中、底部或拉伸。`productionGuide.relationships` 提供实际来源树、几何候选和状态所有者；合并后给出原生容器承接关系。推断不能自动覆盖制作决定，映射不等于已呈现，未知项保留为非阻断待办。

复刻时先从截图和实际几何确定区块边界，再确定容器职责，最后选择小组件。不要先把组件逐个放上页面，再靠 CSS 修正整体方向。此规则适用于不同网站；具体宽度、间距、断点和分栏比例只来自当次来源与目标能力。

## 自外向内建树

1. **页面内容线**：分别记录页眉与正文的内容左/右边界、最大宽度和手机边距。背景可以通栏，但内容应进入同一限宽轨道；`max-width` 不是“左对齐线”的替代品。
2. **大板块**：一个可独立理解的视觉区块先有一个父容器。父容器负责背景、内容宽度、内边距和子项主方向。只有来源有明确的内部分层时才继续嵌套。
3. **子容器**：按内容组而非单个文字/图片拆分。每层明确横排或竖排、换行、对齐、间距、占比和响应式变化。四列页脚是横排父容器加四个纵排子容器，不是四个窄组件并排。
4. **叶子组件**：标题、正文、图片、按钮、菜单等放在负责它们的最小容器内；不为每个组件机械加一层。小组件只处理自身内容和局部样式。

例如“运费提示＋Shop Your Teams”：外层内容轨道纵排；第一子容器放运费文字，第二子容器横排，左侧为标题/收藏链接纵排，右侧为联赛图标横排；图标各自为纵排的图片＋名称组。手机方向与宽度用已注册的原生响应式控件表达。

例如页脚：外层背景及内容轨道，第一子容器横排四列，每列纵排标题、链接或按钮；下面另设法律链接组及版权组。桌面四列宽度由父子容器共同决定，不能同时用四等分网格和每个子容器 `25%` 再分一次。

## Elementor 落地和验收

- 先核对目标站真实注册的 Container 控件；方向、宽度、换行、间距、对齐优先写原生 settings。CSS 只补原生无法表达的细节，不反向覆盖原生布局和设备显隐。
- 盒式容器的直接内容通常在 `.e-con-inner`；全宽容器的子元素通常直接位于容器下。不要把两种 DOM 结构当成同一种，或靠错误的子选择器获得偶然效果。
- 复核每层的实际 `getBoundingClientRect()` 和计算样式：外层轨道是否与页眉/正文对齐，子项方向与比例是否正确，文字是否因二次分栏被挤窄，手机是否出现横向溢出。
- 新任务在生成前冻结上述树与双桌面/双手机几何决定；已有任务只有当前用户明确授权时才改树。对自有草稿可使用 `replica:full revise-layout --run-dir ... --plan ... --expected-fingerprint ...`：它只允许已注册的原生布局控件、相邻元素分组和原组件保留，并在服务器 CAS 写入后读回。长文本可把相邻标题与正文 Widget 原样移入新的 Container，以原生 `overflow: auto` 和来源高度形成独立滚动视口；不能改变 Widget 内容或用 CSS 假装分组。任何未知写入先对账，不重复创建或盲写。
- 结构变化会使旧视觉验收失效；保存后重新检查桌面与手机实际页面和交互，不能用合法 JSON 或单元测试代替。
